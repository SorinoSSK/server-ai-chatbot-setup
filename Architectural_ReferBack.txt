  Key weaknesses to weigh

  1. Public ingress punches a hole in your isolation goal
  Step 1's entire purpose is isolating this stack from the network. But step 6
  requires a public URL. You need one narrow, dedicated ingress point (reverse
  proxy / tunnel, e.g. Traefik, Nginx, or Cloudflare Tunnel) that exposes only
  the Review API's token‑validated endpoints — never the repo container, agent
  container, or RabbitMQ directly.

  2. Token-in-URL as sole first factor has known leak vectors
  - Browser history, Referer headers, proxy/CDN logs, Telegram message
    forwarding.
  - Mitigations (all standard, all optional to implement now):
    - Server-side TTL enforcement (don't trust a JWT exp alone — track
      "used/expired" state).
    - Single-use or single-session tokens; invalidate on first successful load,
      not just after decision.
    - Avoid embedding the token in a query string where possible (path segment
      is marginally better; avoid GET-with-Referer-leak to third-party assets on
      the review page).
    - The bearer token idea is good as a genuine second factor (something
      Telegram-side, something link-side) — just ensure it's checked server-side
      on every review action, not just on page load.

  3. "Git-like docker" — don't expose git protocol publicly
  Two repo categories exist:
  - GitHub-hosted repos: agent can clone/fetch normally using scoped credentials
    held only inside the repo container.
  - Host-only repos (never touch cloud): keep as bare repos on the host; agent
    works against a local clone/worktree inside its sandbox.

  For review, you don't need to expose git at all to the frontend. The repo
  container should generate a diff/patch artifact + metadata (files changed,
  test results, commit message) and hand that off — the frontend/reviewer only
  ever sees a diff payload, not a live git endpoint. This is smaller attack
  surface, keeps host-only repos fully off any public path, and avoids having to
  secure a git server for the internet.

  4. Should there be a separate Review API container? — Yes, recommended
  Don't let the repo/pipeline container (step 5) be the thing Netlify talks to.
  Reasons:
  - Step 5's container holds git credentials and pipeline execution — it should
    never be internet-facing.
  - A thin Review API / BFF container should:
    - Consume "diff ready" events from RabbitMQ (or receive them via internal
      call from step 5).
    - Mint/validate the tokenised link and bearer token.
    - Serve the diff to the frontend, accept approve/reject, and publish the
      decision back onto RabbitMQ for the agent to act on.
    - Enforce TTL/expiry and trigger Telegram (via step 2) to re-issue a link on
      expiry.
  - This mirrors your existing mediaAPI pattern (route + SSE + queue utilities)
    — you could realistically reuse sse_registry.py/queue.py-style patterns here
    for pushing live diff status to the frontend instead of polling.

  5. Multi-tenant agent container (step 3)
  Housing agents from different organisations in one container is the biggest
  risk in the plan if it means shared filesystem/process space. Recommend (as an
  option, not a requirement) per-agent or per-org container/namespace isolation
  — otherwise a bug or prompt-injection in one agent's context could reach
  another org's credentials, sandbox, or repo cache. At minimum: separate
  filesystem volumes, separate credential scopes, no shared memory/session
  state.

  6. Sandbox test/deploy execution
  "Test, pull, push, modify" implies the agent may need to run code (spin up
  test runners, maybe containers). If it needs Docker-in-Docker or Docker socket
  access, that's a significant privilege escalation risk — worth flagging now
  even though you're not implementing yet. A safer pattern is ephemeral,
  disposable sandbox containers per test run rather than a long-lived sandbox
  with broad exec rights.

  7. "Agent can only pull when allowed, but can always push for review"
  Good default-deny design. Just make sure the enforcement lives server-side (in
  the repo container / gateway), not as an instruction the agent merely agrees
  to follow — otherwise it's a policy, not a control.

  8. Database — not yet considered, but will be needed for
  - Token/session store with TTL (Redis is a natural fit given your expiry-based
    design).
  - Repo registry (which sandbox/credentials map to which repo, GitHub vs
    host-only).
  - Audit log of push → review → approve/reject → deploy (important given this
    affects production code and host backups).
  - No implementation needed now — just flagging it as a dependency of steps
    5/6/Review API before those are built.

  - New container for the review endpoint API: yes, recommended as a separate,

  How code actually gets into the sandbox (your concern)

  Three real options — pick based on whether host-only repos are involved:

  Approach: Bind-mount the working copy
  How it works: Repo container checks out the agent's branch/worktree to a
  shared
  internal volume; orchestrator mounts that path (RW) into the ephemeral
  container.
  Fit here: Simple, fast — but the sandbox container now has filesystem access
  to
  a path other agents' tasks might also touch if the shared directory isn't
  per-task scoped. Needs strict per-task subdirectories, not a shared root.
  ────────────────────────────────────────
  Approach: Git clone inside the sandbox at boot
  How it works: Orchestrator hands the sandbox container a short-lived, scoped
  credential (or points it at your internal-only git service) and it clones
  fresh.
  Fit here: Clean and reproducible, but means transient git credentials exist
  inside a container running possibly-untrusted agent code — needs credentials
  to be single-use/expiring and never the agent's own long-lived PAT.
  ────────────────────────────────────────
  Approach: CI-style ephemeral image build (recommended)
  How it works: Repo container produces a patch/tarball of the exact commit
  under
  test → Orchestrator builds a throwaway image (base image + COPY  code) → runs
   it → discards image and container after.
  Fit here: No bind mount to host filesystem at all, no credentials inside the
  sandbox (repo container never hands out git access, just code), and it's the
  same trusted pattern most CI systems (GitHub Actions runners, GitLab CI)
  already use. Best isolation for agent-generated code specifically.

  Given you're worried about "how code is brought over," the CI-style build is
  the strongest fit: the sandbox never needs git, never needs a shared
  filesystem with other agents, and every run starts from a known-clean base
  image. The trade-off is slightly more build time per test run and you need a
  lightweight internal registry or build cache if base images are reused often.

  Other things a "disposable sandbox" needs, regardless of which option you pick

  - Hard resource limits per container: CPU/memory/pids caps and a wall-clock
    timeout, so a runaway or intentionally malicious test can't exhaust the
    host.
  - No privileged mode, run as non-root, default seccomp/AppArmor profile —
    standard, but worth stating since this container runs code an AI wrote,
    which is a higher-risk source than human-authored CI jobs.
  - Network egress policy: default-deny, with an explicit allowlist if the code
    under test needs package registries (npm/pip/etc.). Don't give sandboxes
    free internet by default.
  - Ephemeral only — no persistent volumes surviving the run, no shared writable
    state between test runs, so nothing leaks between tasks/agents.
  - Stronger sandbox runtime if you want extra headroom: gVisor or Kata
    Containers instead of the default runc, since the workload is inherently
    less trusted than normal CI. Optional, not required — flagging as a future
    hardening step, not a must-do now.

● What this pattern is

  This is essentially a multi-agent debate / adversarial-collaborative pattern:
  two (or more) agents each propose a solution, critique each other's proposal,
  revise, and converge on a merged result — with a scoring layer ("weightage")
  that must be evidence-based rather than the agents just asserting confidence.
  Architecturally, this needs a third, non-partisan role — an arbiter — that
  neither agent controls, otherwise "weightage" is just whichever agent argues
  more persuasively, not whichever is objectively better.

  Where it fits in what you've already designed

  You don't need a brand-new container family for this — it slots in as a new
  logical role sitting between your agent queues and the repo/review pipeline:

  queue2 (Agent A) ──┐
                      ├──► Debate Orchestrator ──► Sandbox Orchestrator (runs
  each proposal, per-agent isolated)
  queue3 (Agent B) ──┘            │                        │
                                   │◄── objective evidence ─┘ (test results,
  lint, security scan, perf)
                                   │
                          apply scoring rubric
                                   │
                       converged? ──no──► send critique + scores back to both
  agents → next round
                                   │
                                  yes
                                   │
                                   ▼
                      Repo Container (produce merged diff artifact)
                                   │
                                   ▼
                      Review API (tokenised link + bearer token)
                                   │
                                   ▼
                  Telegram Bot → user: weightage summary + references + review
  link

  The Debate Orchestrator is a deterministic coordinator (not itself an LLM
  making judgment calls) — its job is process control and score calculation, not
  opinion.

  Making "weightage" evidence-based, not blind

  The key requirement you stated — "with references and not blind weight" —
  means the score has to be traceable to something reproducible. Recommend a
  fixed, versioned rubric rather than letting agents decide their own weighting
  each round:

  ┌─────────────────┬────────────────────┬─────────┬───────────────────────┐
  │    Criterion    │  Evidence source   │ Example │     Why objective     │
  │                 │                    │  weight │                       │
  ├─────────────────┼────────────────────┼─────────┼───────────────────────┤
  │ Tests pass /    │ Sandbox            │         │ Deterministic         │
  │ coverage delta  │ Orchestrator run   │ 40%     │ pass/fail,            │
  │                 │ output             │         │ reproducible          │
  ├─────────────────┼────────────────────┼─────────┼───────────────────────┤
  │ Static analysis │ Linter/security    │         │ Tool-generated, not   │
  │  / lint         │ scanner output     │ 20%     │ agent-asserted        │
  │ conformance     │                    │         │                       │
  ├─────────────────┼────────────────────┼─────────┼───────────────────────┤
  │ Adherence to    │ Diff against style │         │ Checkable against     │
  │ existing repo   │  baseline / prior  │ 15%     │ actual codebase       │
  │ conventions     │ commits            │         │ history               │
  ├─────────────────┼────────────────────┼─────────┼───────────────────────┤
  │ Performance (if │ Benchmark run in   │ 15%     │ Measured, not claimed │
  │  relevant)      │ sandbox            │         │                       │
  ├─────────────────┼────────────────────┼─────────┼───────────────────────┤
  │                 │                    │         │ Kept small            │
  │ Peer critique   │ Agent-vs-agent     │ 10%     │ deliberately — this   │
  │ (subjective)    │ commentary         │         │ is the only "opinion" │
  │                 │                    │         │  component            │
  └─────────────────┴────────────────────┴─────────┴───────────────────────┘

  The rubric itself should be a plain config (ideally version-controlled,
  human-editable) so you — not the agents — control how much subjective critique
  is allowed to matter. This is a design choice, not a fixed requirement; you
  may weight it differently per repo.

  Each score in the final summary should carry a reference: which test run ID,
  which scan report, which prior commit was used for comparison — so when this
  reaches Telegram, the user isn't shown "Agent A: 82%, Agent B: 71%" with no
  backing, but "Agent A: 82% — 18/18 tests passed (run #4471), 0 security
  findings (scan #229)…".

  Convergence and termination — this needs hard limits

  Adversarial loops between two LLM agents can oscillate without a stop
  condition. The orchestrator should enforce:
  - Max rounds (fixed cap, not open-ended).
  - Convergence threshold (e.g. score delta within X% counts as "agreed").
  - Explicit stalemate path: if max rounds hit without convergence, don't force
    a merge — send both proposals with their evidence to the user via Telegram
    and let the human decide. This fits your existing "human approves via review
    link" flow rather than fighting it.

  Isolation carries over from the sandbox discussion

  Each agent's proposal should still run in its own ephemeral sandbox (per the
  CI-style disposable container model from before) — don't let the two agents
  share a test environment during the debate, especially if they could belong to
  different orgs per your multi-tenant queue design. Otherwise one agent's test
  run could interfere with or observe the other's, undermining the "counter"
  fairness the pattern relies on.

  Weaknesses to weigh

  - Cost/latency: every round is a full LLM turn + a full sandbox test run for
    each side — multiply by round count. Worth capping rounds tightly and
    possibly short-circuiting if one proposal fails tests outright (no need for
    a full debate round if one side doesn't even build).
  - Gaming the rubric: if too much weight sits on "peer critique"
    (agent-vs-agent opinion) rather than tool-generated evidence, an agent could
    win by argument quality rather than code quality. Keep the subjective slice
    small, as above — this is exactly what you flagged wanting to avoid.
  - Rubric transparency vs. rigidity: a fixed rubric is auditable but may not
    fit every repo (e.g. performance criteria irrelevant for a config-only
    change). Consider making the rubric per-repo configurable rather than global
    — optional, not required now.
  - User fatigue: if every task produces a multi-round debate summary, Telegram
    messages could get long/noisy. Worth deciding upfront whether the user
    always wants the full weightage breakdown or just a collapsed summary with a
    link to full evidence (which the Review API/frontend could host, keeping
    Telegram itself terse).
