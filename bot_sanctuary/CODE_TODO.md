# TODO Record for Bot Sanctuary

## Purpose

`bot_sanctuary` is the successor to `bot_orchestrator`'s routing role, merged with the AI agent pipeline itself — one consolidated Python application rather than a separate orchestrator container plus per-agent containers. It owns: RabbitMQ consumption from `telegram_gateway`, per-session threading, the multi-agent "Call" pipeline (via the Claude Agent SDK), tool access, and error/alert routing.

**Confirmed:** `bot_orchestrator_application` is being retired in favour of this single application. `bot_orchestrator`'s already-planned responsibilities (SMTP alerting, session-reset broadcast, task routing, outbound payload validation — see its own `CODE_TODO.md`) are absorbed here, refined per the sections below.

Status: **Planned, not yet implemented.** Design being drafted across architecture discussion; several items below are proposed and awaiting confirmation, marked accordingly.

---

## 1. Container & runtime

- [ ] Base image: `python:3.x-slim` (not a generic Linux+Node image — see rationale below).
- [ ] `claude` CLI installed via the native installer (`curl -fsSL https://claude.ai/install.sh | bash`) — Node-free, auto-detects host architecture. Used for manual/admin actions only (`claude setup-token`, `claude doctor`), not by the app itself.
- [ ] `claude-agent-sdk` installed via `pip` — used programmatically by the app for the actual session pipeline. Bundles its own native binary per-platform; confirmed wheels exist for `manylinux_2_17_aarch64` (covers Raspberry Pi) and the equivalent x86_64 wheel for the eventual AMD deployment target.
- [ ] **Confirmed:** build as a multi-arch image (Docker Buildx, `--platform linux/amd64,linux/arm64`) — must run on both the AMD64 production host and the Raspberry Pi. Verify post-build on both targets that the SDK resolved a proper wheel (not a source-dist fallback with no bundled binary).
- [ ] `CLAUDE_CONFIG_DIR` set to a path on the secondary disk — used for both relocated logs and the manually-placed OAuth credential (below).

## 2. Authentication — manual, dual-method, no automated injection by default

- [ ] **Confirmed: no automated credential injection as the primary path.** The administrator authenticates personally, either:
  - **Method A — in-container login:** `docker exec` into the container, run `claude setup-token` (loopback port published, or SSH `-L` tunnel if the host is remote), complete the browser step, then manually write the printed token into `${CLAUDE_CONFIG_DIR}/oauth_token`.
  - **Method B — generate elsewhere, place later:** run `claude setup-token` on any other browser-capable device (no container network exposure needed at all), store the token, then `docker exec` in later and write it into the same `${CLAUDE_CONFIG_DIR}/oauth_token` file.
  - **Confirmed: both methods are supported**, resolved by the same credential loader (below) — not an either/or choice baked into the code.
- [ ] Credential resolution order, checked at each `start_new_session()` call:
  1. `CLAUDE_CODE_OAUTH_TOKEN` environment variable, if present (covers a future/optional injection path — not used by default, but the resolver doesn't hard-block it).
  2. Else, read `${CLAUDE_CONFIG_DIR}/oauth_token` from disk.
  3. Else — **container does not crash or exit.** The main process (queue consumer, exec-accessible shell) stays alive; only that specific session request goes into a pending/"waiting for authentication" state until a credential becomes available. Open sub-decision: auto-retry on an interval vs. only re-check on next explicit trigger — not yet decided.
- [ ] **Note (not a container-security boundary):** the OAuth token is a portable bearer credential, not device/container-bound — anyone holding the string can use it from anywhere until expiry/revocation. File permissions on `oauth_token` should be restrictive (`0600`); the secondary disk holding `CLAUDE_CONFIG_DIR` is a meaningful thing to protect/exclude from loosely-handled backups.
- [ ] `setup-token` chosen deliberately over `/login` — avoids the documented `--print` mode OAuth refresh bug (access token expiry ~8h, refresh not persisted correctly in headless/print automation). `setup-token`'s long-lived (1-year) static token sidesteps this.

## 3. RabbitMQ + threading model

Status: **RabbitMQ connectivity layer and session routing (`SessionWorker`) both implemented.** `utilities/utils_session/session_worker.py` (new), `utilities/utils_queue/message_handler.py`, `utilities/utils_redis/database.py`, `config.py` all updated. **The agent Call pipeline itself (§5) is still not implemented** - a `SessionWorker` fully receives, coalesces, and logs what it would do with a batch of messages, but never actually invokes an LLM or replies. That remains the next piece to build.

- [x] Single shared RabbitMQ **consume** connection/channel, read by one background consumer thread (`queue_consume_task()`, started via `start_queue_consumer()`) — `Q_CHANNEL_IN` (`telegram_gateway_outbound_queue` by default) is what this application consumes.
- [x] Startup connection retries indefinitely rather than crash-exiting (`initialise_rabbitmq_connection()`) - same infinite-retry-at-startup pattern already fixed in `telegram_gateway` (see its own `CODE_TODO.md`), built in here from the start rather than retrofitted later.
- [x] `message_handler.py::process_message()` decodes each message and determines its effective type, then branches: `_handle_gateway_alert()`/`_handle_gateway_recover()` (§4), `_handle_session_cleared()` (stops and removes the corresponding `SessionWorker`, if one exists), and `_dispatch_to_session()` (routes to `get_or_create_session_worker(session_id).submit(data)`).
- [x] `RabbitMQPublisher` class (`utils_queue/queue.py`) - now actually instantiated: once per `SessionWorker` (its own long-lived connection, confined to that worker's thread for its whole life), and once per short-lived "intermediate task closer" thread spawned by a coalesced batch (see below) - each such thread creates, uses, and closes its own disposable instance rather than sharing the `SessionWorker`'s.
- [x] **Confirmed, implemented as originally decided:** each `SessionWorker` owns its **own** RabbitMQ connection for publishing back to `telegram_gateway` — not a single shared connection guarded by a lock. Per Pika's own thread-safety guidance (a lock around a shared connection's `basic_publish` is insufficient - the I/O loop is tied to its owning thread), per-thread connections is the adopted, now-implemented approach.
- [x] **Confirmed and implemented — routing key is `session_id`, thread lifetime spans multiple tasks, not one thread per message.** `get_or_create_session_worker()`/`remove_session_worker()` (`utils_session/session_worker.py`) form the registry (`dict[str, SessionWorker]`, guarded by a `threading.Lock` scoped only around the get-or-create/remove check, never around a worker's own processing). Each `SessionWorker` loops `inbox.get()` → coalesce → dispatch → repeat (see the new coalescing item below), so multiple tasks arriving for the same session are processed strictly one batch at a time, in arrival order.
  - **Not yet implemented: the actual Claude Agent SDK session/client state a `SessionWorker` is meant to own** (§5) - a worker today only logs what it would send to the pipeline. Verifying against the SDK's persistent multi-turn client API remains open, deferred to §5.
- [x] **`gateway_alert`/`gateway_recover` are checked for before session routing runs, not left to fall through** - both carry `session_id: null` and are dispatched straight to §4's SMTP path (see `process_message()`). `session_cleared` stops the corresponding `SessionWorker` via `remove_session_worker()` + `.stop()`.

### New: message coalescing, and the task_id-orphaning issue it creates

**Context - why coalescing at all.** `telegram_gateway` already combines every media upload with its finalising caption/text into one task before ever pushing it (see its own README's draft-flow docs) - by the time a task reaches `bot_sanctuary`, it is always one complete unit already. The one case with no equivalent combining is plain text: every text update becomes its own `task_id`/RabbitMQ message immediately, with no debounce. Discussed at length in chat (not reproduced in full here): a fixed-delay debounce in `telegram_gateway` was considered and rejected - it taxes every message with latency to solve a rare case, reintroduces the exact "renewed timer never expires" bug this project has already hit and fixed twice elsewhere (`POLL_GLOBAL_CAP_SECONDS`, the `gateway_alert` throttle's own non-renewed TTL), needs new persisted-timer infrastructure `telegram_gateway` shouldn't own, and weakens `session_reset`'s open-task protection (a message sitting in an undeclared debounce buffer has no `task_id` yet, so `has_open_tasks()` can't see it). **Decided instead: coalesce at `bot_sanctuary`'s own dequeue time** - `SessionWorker._run()` blocks for one message, then non-blockingly drains whatever else is already queued (`Option A` - checked right before/at the point a turn would start, not via a fixed timer) into one combined batch. Zero added latency for the common single-message case; only ever combines what's genuinely already waiting.

**The issue this creates, flagged and now resolved:** each message in a coalesced batch still carries its own distinct `task_id` from `telegram_gateway`. If the whole batch is treated as one turn and only acknowledged once the (eventual) agent reply is ready, every `task_id` except the reply's own would stay "open" under `telegram_gateway`'s `session_tasks:<chat_id>` for the *entire* turn duration - and if the reply is only ever published against one `task_id`, the others would never close at all, permanently blocking a future `session_reset` for that chat (deferred forever, until `PENDING_RESET_MAX_WAIT_SECONDS` eventually force-applies it - self-healing, but not clean).

**Resolution (user's proposal, implemented):** every `task_id` in a coalesced batch *except the last* is closed out immediately - `{"task_id": ..., "type": "completed"}` (`telegram_gateway`'s existing terminal marker: "no further payloads are expected... triggers cleanup only", no reply sent) - published on a **separate, short-lived thread** (`_close_intermediate_task_ids()`), concurrently with whatever the `SessionWorker`'s own thread does next, so this never delays the actual turn. Only the batch's **last** `task_id` stays open and is the one the eventual real reply (§5) must be published against. This required zero `telegram_gateway` changes - `completed`'s existing contract already does exactly what's needed.
  - **Why a separate, disposable `RabbitMQPublisher` for the closer thread, not the `SessionWorker`'s own:** `RabbitMQPublisher` is documented as confined to exactly one thread for its whole life; sharing the `SessionWorker`'s long-lived instance across two threads would violate that. The closer thread creates, uses, and closes its own instance instead - a small, bounded, infrequent extra connection cost (only when a batch actually has more than one message), not a hot-path concern.
  - Each successfully-closed intermediate `task_id` also calls `mark_task_complete()` (see the new crash-recovery tracking below) - a byproduct of this mechanism is that part of that tracking's "mark complete" hook is *already* wired, ahead of §5, for every task_id closed this way. Only the batch's final `task_id` still depends on §5 to ever call it.

### New: crash-recovery tracking (`utils_redis/database.py`, not yet fully wired)

- [x] `mark_task_active(task_id, session_id)` - called from `SessionWorker.submit()`, in the same synchronous window as the RabbitMQ ack, durably recording (Redis `HASH`, no TTL) that this application has accepted responsibility for a `task_id`.
- [x] `mark_task_complete(task_id)` - clears that record. Wired today for every intermediate `task_id` closed by the coalescing resolution above; **not yet wired for a batch's final `task_id`**, since that depends on §5 actually existing and calling it on every exit path (success, error, and any future cancellation).
- [x] `sweep_orphaned_sessions()` - returns everything still recorded as active.
- [x] **`resync_orphaned_sessions()` (`utils_session/session_worker.py`) - now wired into `initialise.py`, per explicit instruction to proceed despite the interim caveat below.** Runs after `initialise_rabbitmq_connection()` succeeds but **before** `start_queue_consumer()` starts - deliberately, so no new session-routed task can mutate the active-task record while the sweep is reading/grouping/clearing it (mirrors `telegram_gateway`'s own ordering precedent: its `resync_pending_resets()` also runs before Telegram polling resumes, not after).
  - Groups every still-active `task_id` by `session_id`, publishes exactly one `{"task_id": <any one of that session's task_ids>, "type": "session_reset"}` per distinct session (its existing, already-supported "orchestrator requests a reset" contract - see `telegram_gateway/README.md`'s `session_reset` payload) - zero `telegram_gateway` changes needed. **Deduped by `session_id`, not sent once per orphaned `task_id`** - a second reset request referencing a `task_id` whose chat was already wiped by the first would fail to resolve `chat_id` at all.
  - On a successful publish, **every** `task_id` belonging to that session is cleared (`mark_task_complete()`), not just the one used to build the request - otherwise the others would linger, incorrectly looking "still active" to the next sweep. A failed publish leaves that session's entries untouched entirely, to be retried on the next startup rather than lost.
  - **Self-healing interaction confirmed, not incidental:** the recovered session's own orphaned `task_id` is *also* still "open" on `telegram_gateway`'s side (it never got `completed`/`error` either), so the reset request will likely defer rather than apply instantly - exactly the case `telegram_gateway`'s own `PENDING_RESET_MAX_WAIT_SECONDS` ceiling already exists for ("an agent bug, crash, dropped message" - see its README). Once it force-applies, the chat still receives `RESET_NOTICE_MESSAGE` - so the original ask ("user will get to know of the issue if session clearing happens often enough") holds even though the reset itself may not be instant.
  - **Known interim behaviour, accepted, explicit instruction to wire this now regardless of it:** until §5 reliably calls `mark_task_complete()` for a batch's final `task_id` on every exit path, *every* task ever accepted still looks "active" after any restart - including an ordinary clean redeploy, not just a genuine crash - so this currently requests a `session_reset` for every chat with any unresolved history on every startup. Previously deferred for exactly this reason; now shipped ahead of §5 per explicit instruction rather than waiting. Revisit/narrow once §5 exists and this over-triggering is no longer acceptable.

### Open decisions - three of four now decided and implemented; stray-message handling still on hold

- [x] **Inbox overflow - decided and implemented.** Each `SessionWorker`'s inbox is a bounded `queue.Queue(maxsize=SESSION_INBOX_MAX_SIZE)` (new `config.py` setting, default `100`). Overflow is drop-newest with a `logger.critical()` - chosen over blocking `put()`, which would stall the single shared RabbitMQ consumer thread (and therefore every other session, plus `gateway_alert`/`gateway_recover`) behind one stuck session's full inbox.
- [x] **RabbitMQ ack timing - decided ("return Ack after successfully registering into queue of that session's mailbox") and implemented.** `_dispatch_to_session()` calls `submit()`; a successful registration (`True`) returns normally and `process_message()`'s caller acks right after, same as every other message type. A failed registration (`submit()` returns `False` - inbox full) now **raises** instead of being silently swallowed, so the message is *not* acked - it propagates to `queue_consume_task()`'s existing generic handler, which nacks with requeue up to `Q_CONSUME_MAX_ATTEMPTS` before finally dropping it (no `queue.py` changes needed). A missing `session_id` remains a plain logged drop, not a raise - it's permanently malformed, not transient, so redelivery would never help. At-least-once still weakens for whatever's sitting queued-but-unprocessed at the moment of a crash (an already-acked, already-registered message) - that gap is what the crash-recovery tracking above exists to detect and recover from after the fact, rather than trying to prevent (a deferred-ack alternative was considered and rejected in chat - it needs `add_callback_threadsafe()` cross-thread ack plumbing, a lock around the RabbitMQ consumer's own per-message retry counter, and introduces its own new correctness gap: a delivery_tag becomes stale/invalid across a consumer reconnect, which already happens automatically on a dropped connection).
- [ ] **Stray message after `session_cleared`. On hold, per explicit instruction - no change.** `get_or_create_session_worker()`'s "create if missing" would resurrect a worker for a late message tagged with an already-cleared `session_id`, rather than recognising it as stray and dropping it. Narrow risk in practice (`telegram_gateway` never reuses a `session_id` after a reset, so this only bites on genuine out-of-order delivery) - accepted for now, revisit if ever observed.
- [x] **Shutdown behaviour for in-flight workers - decided ("send shutdown signal to all thread to inform them to finish last task before closing; last task will be marked completed when a response is given to telegram_gateway") and implemented.** `SessionWorker` now has two independent stop paths, not one:
  - `stop()` (unchanged) - immediate, sets a `threading.Event`, abandons whatever else is queued. Still the one used by `_handle_session_cleared()` - correct there, since `telegram_gateway` has already wiped that `session_id` on its own side, so anything left queued would only ever produce an orphaned reply.
  - `shutdown()` (new) - sets a second, independent `threading.Event`. The run loop keeps draining and processing whatever's queued, batch by batch, without waiting, until the inbox is genuinely empty *and* `shutdown()` has been called - so a backlog queued right as shutdown begins is still fully processed, not just whatever batch was already in flight. Every item drained this way was already acked off RabbitMQ (per the ack-timing decision above), so abandoning it here would be a real message loss, not a stale/orphaned one - the opposite judgement from `stop()`.
  - New `shutdown_all_session_workers()` (`utils_session/session_worker.py`) - snapshots the session registry, calls `shutdown()` on every worker, then `join()`s each thread (bounded by new `config.py` setting `SESSION_SHUTDOWN_TIMEOUT_SECONDS`, default `30`s, `0` = wait indefinitely). A worker still alive once its timeout elapses is logged and abandoned - the process exits regardless, since this only ever runs from `terminate_application()`.
  - Wired into `utilities/initialise.py::terminate_application()` **after** `stop_queue_consumer()` (so no new task can reach a worker already shutting down) and **before** `close_rabbitmq_connection()`/`close_redis_connection()` (a worker finishing its last batch may still need to publish and call `mark_task_complete()`).
  - **"Last task marked completed when a response is given to telegram_gateway" is a structural link to §5, not yet literal** - `_process_batch()` today only logs what it would do (§5 doesn't exist yet); once it does, and runs synchronously inside the run loop as it does now, `join()`ing a worker's thread here is exactly what lets an in-flight turn actually finish (publish the real reply, call `mark_task_complete()`) before the process exits, rather than its daemon thread being cut off mid-turn by the interpreter shutting down underneath it.

## 4. Error handling — two distinct alert paths

Status: **SMTP send/test capability implemented and now wired into `gateway_alert`** (`utilities/utils_smtp/smtp_handler.py`, `utilities/utils_queue/message_handler.py::_handle_gateway_alert()`, `utilities/utils_redis/database.py`, config in `config.py`). Throttling is implemented (Redis-backed, durable across restarts); non-blocking dispatch is **not** implemented - `send_mail()` still runs synchronously on the RabbitMQ consumer thread, see the open item at the end of this section. `bot_orchestrator` (the source of the original "reuse its SMTP groundwork" plan below) has since been retired and removed from the repository entirely - this section's own implementation is now authoritative, not a carry-over.

- [ ] Errors **originating from `telegram_gateway`** (Telegram itself unreachable) → routed to **SMTP** (Telegram can't be used to notify the user if Telegram is what's down).
- [ ] Errors **from Claude/the agent backend** (API down) → sent **to `telegram_gateway`** → surfaced to the user via Telegram directly (Telegram itself is presumably fine in this case).
- [x] **SMTP configuration + send/test capability implemented**, directory-structure convention mirroring `telegram_gateway` (a per-domain `utils_X/` folder under `utilities/`) - named `utils_smtp/` (not `utils_email/`, per explicit instruction, superseding the old `bot_orchestrator`-era naming below):
  - `config.py`: `SMTP_ENABLE_MAILER` (bool, default `False` - `send_mail()` is a no-op until turned on), `SMTP_FORCE_SSL` (bool), `SMTP_AUTH_TYPE` (str, default `"LOGIN"` - only `"NONE"`, case-insensitive, is treated specially, skipping authentication entirely; smtplib's own `.login()` negotiates the actual SASL mechanism itself, so no further distinction between mechanism names is made), `SMTP_SKIP_TLS` (bool), `SMTP_HOST`, `SMTP_PORT` (default `587`), `SMTP_FROM_EMAIL`, `SMTP_TO_EMAIL` (default alert recipient - resolved by `test_smtp_configuration()`/future `gateway_alert` wiring rather than requiring one be passed manually every time), `SMTP_USERNAME`, `SMTP_PASSWORD`. A separate `SMTP_FROM_NAME` was considered and dropped in favour of reusing the new **Bot Identity** section's `TELEGRAM_BOT_NAME` (same env var name/convention as `telegram_gateway/config.py`, both fed from the same root `config.ini` `CHATBOT_NAME` value) - so mail sent by this application identifies as the same persona the user already talks to on Telegram, rather than a second, separate name.
  - `utils_smtp/smtp_handler.py`: `send_mail(subject, body, to_addresses)` - connects per `SMTP_FORCE_SSL`/`SMTP_SKIP_TLS` (implicit TLS / STARTTLS / no TLS), authenticates unless `SMTP_AUTH_TYPE="NONE"`, sends a plain-text `MIMEMultipart` with its `From` header built via `email.utils.formataddr((TELEGRAM_BOT_NAME, SMTP_FROM_EMAIL))` (handles quoting the display name if it ever needs it; falls back to the bare address if `TELEGRAM_BOT_NAME` is unset). The SMTP envelope sender passed to `sendmail()` stays the bare `SMTP_FROM_EMAIL` regardless - only the header display name changes, per RFC. `test_smtp_configuration(to_address=None)` - sends one fixed test email; recipient resolves `to_address` (explicit override) → `SMTP_TO_EMAIL` (configured default) → `SMTP_FROM_EMAIL` (send-to-self fallback), in that order.
  - **Masking, per explicit instruction ("mask from mail, username, and password"):** `_mask()` never reveals any part of `SMTP_FROM_EMAIL`/`SMTP_USERNAME`/`SMTP_PASSWORD` in a log line, not even a partial value - only `"<set>"`/`"<unset>"`. Chosen over a partial-reveal scheme (e.g. `jo***@domain.com`) since no specific masking format was mandated and full opacity is the safer default for a credential; open to revisiting if a partial reveal is actually wanted for easier operator debugging. `TELEGRAM_BOT_NAME` and `SMTP_TO_EMAIL` are logged in the clear - the former is a public display name, not a secret; the latter is masked instead at the `config.ini`/`config_sample.ini` generation level (see below), consistent with how `SMTP_FROM_EMAIL` is treated there too.
  - **Manually triggerable via a docker command, deliberately not run automatically at startup:**
    ```
    docker exec <container_name> python -m bot_sanctuary_application.utilities.utils_smtp.smtp_handler
    docker exec <container_name> python -m bot_sanctuary_application.utilities.utils_smtp.smtp_handler someone@example.com
    ```
    The module's own `if __name__ == "__main__":` block sets up logging (mirroring `main.py`'s own startup sequence) and calls `test_smtp_configuration()`, exiting `0`/`1` on success/failure.
  - `config.ini`/`config_sample.ini` (root-level): matching `CHATBOT_SMTP_*` variables added under `BOT SANCTUARY CONFIG`, wired through both `bot_sanctuary/setup.sh`'s `bs_dev_run_docker()` (`-e "SMTP_*=..."`/`-e "TELEGRAM_BOT_NAME=${CHATBOT_NAME}"`, `docker run` path) **and** `compose.dev.yml`'s `bot-sanctuary` service `environment:` block (`docker compose` path) - both needed, since `setup.sh` initially only had `docker run` covered. No new root variable was added for the bot name itself - both `telegram_gateway` and this application now read the same root `CHATBOT_NAME` value, just via each service's own `TELEGRAM_BOT_NAME` env var. `CHATBOT_SMTP_FROM_EMAIL`/`TO_EMAIL`/`USERNAME`/`PASSWORD` are `REPLACE_WITH_...` placeholders in `config_sample.ini`; `config.ini` has since been filled in with real Resend credentials and a real recipient directly by the user (`CHATBOT_SMTP_ENABLE_MAILER="true"`) - `setup.sh`'s `get_masked_config_variables()` (used by "Generate config_sample.ini") was updated to include all four so a future regeneration doesn't leak them.
- [x] **`gateway_alert` → SMTP wiring implemented**, with a durable, Redis-backed once-per-day throttle, per explicit instruction:
  - `message_handler.py::_handle_gateway_alert()`: every occurrence is logged critically **and** counted in Redis (`record_gateway_alert_occurrence()`) regardless of whether a notification email actually goes out - this is the "keep track of this error" requirement, distinct from the throttled notification itself. The notification email is gated by `should_notify_gateway_alert()` (Redis-backed, see below) - a suppressed occurrence is logged at INFO, not silently dropped. `mark_gateway_alert_notified()` is only called after a **successful** `send_mail()` - a failed send (SMTP down, `SMTP_ENABLE_MAILER` unset, etc.) deliberately leaves the cooldown untouched so the next occurrence retries, rather than a failed attempt silently consuming the day's one notification.
  - **Message text, verbatim per instruction** (only the persona name is substituted, via `settings.TELEGRAM_BOT_NAME`, same convention as everywhere else it's used):
    ```
    Hello brother,

    <TELEGRAM_BOT_NAME> is having some trouble sending message out of telegram. it appear to be dead, just letting you know that <TELEGRAM_BOT_NAME> might not be available.
    ```
    The user's casual phrasing/grammar ("it appear to be dead") is preserved deliberately, not "corrected" - it's persona voice, not a typo. `<next line>` in the original instruction was read as a paragraph break (blank line) before the body sentence.
  - **Throttle window, per explicit instruction ("once per day, not on every error message"):** implemented as a **rolling 24h cooldown** (`GATEWAY_ALERT_NOTIFY_COOLDOWN_SECONDS`, `config.py`, default `86400`) measured from the last successful notification, not a calendar-day boundary - simpler and avoids timezone/midnight-boundary edge cases. Not yet confirmed this is exactly what "once per day" means to the user (a calendar-day reset would behave differently, e.g. two notifications close together either side of local midnight) - flagged as an assumption, easy to change if a calendar-day reset is actually wanted.
  - **Recipient:** `settings.SMTP_TO_EMAIL` directly (not the `SMTP_FROM_EMAIL` self-send fallback `test_smtp_configuration()` uses - that fallback exists for manual ad-hoc testing convenience, not for this automated path). Guarded explicitly before calling `send_mail()`, since `SMTP_TO_EMAIL=""` would otherwise pass `send_mail()`'s own "no recipient" check (a single-element list containing an empty string is still a non-empty list) and attempt to send to a blank address.
  - **Redis, per explicit suggestion ("we can consider implementing redis with another user login just to do this"):** new `utilities/utils_redis/database.py`, directory/naming convention mirroring `telegram_gateway`'s own `utils_redis/database.py`, but scoped to exactly two keys (`bot_sanctuary:gateway_alert:count`, `bot_sanctuary:gateway_alert:last_notified_at`) - no session/task/draft state, that's a separate, much larger concern (§3's still-unimplemented `SessionWorker` registry) deliberately not conflated with this one.
    - **"Another user login", implemented literally:** a **separate Redis ACL user** for this application (`CHATBOT_BOT_SANCTUARY_REDIS_USERNAME`/`PASSWORD`, new root `config.ini`/`config_sample.ini` variables), sharing the same `chatbot-redis` container as `telegram_gateway` but scoped via Redis ACL key-pattern (`~bot_sanctuary:*`) to only this application's own keyspace - it cannot read/write `telegram_gateway`'s session/task/draft/poll state even though it's the same server. Added as a second `--user` clause on the `redis` service's `redis-server` command in `compose.dev.yml`. `REDIS_DB` also defaults to `1` (vs `telegram_gateway`'s `0`) as a second, belt-and-braces layer of separation on top of the ACL restriction, though ACL key-pattern scoping alone would already be sufficient.
    - **Deliberately not a hard startup dependency, unlike RabbitMQ.** Redis here only backs a durability nicety on an already-optional secondary feature - `_get_redis_client()` connects lazily on first use (the first `gateway_alert` received), with a single attempt, not the infinite-retry-at-startup pattern used for RabbitMQ. `compose.dev.yml`'s `bot-sanctuary` service does get a soft `depends_on: redis: condition: service_healthy` (avoids a cold-start race on the very first alert), but this is a deployment-ordering nicety only - the Python code itself never blocks or crashes on Redis being unavailable, at startup or at any other time.
    - **Fails open on a Redis outage**, deliberately: `should_notify_gateway_alert()` returns `True` (allows the send) if Redis is unreachable, rather than `False`. Reasoning: missing one throttle check occasionally (an over-notification) is judged less harmful than silently suppressing every future alert for as long as Redis happens to be down (a total blackout of the one path whose entire purpose is warning a human that something else is already broken) - an asymmetric risk call, favouring alert availability over perfect throttling. Not yet confirmed this trade-off matches the user's own risk tolerance - flagged, same spirit as the earlier RabbitMQ/Redis-startup-retry "accepted risk" decision.
    - Wired through `bot_sanctuary/setup.sh`'s `bs_dev_run_docker()` (`-e "REDIS_USERNAME=..."`/`-e "REDIS_PASSWORD=..."`, `docker run` path) **and** `compose.dev.yml`'s `bot-sanctuary` service `environment:` block (`docker compose` path), both branches. `CHATBOT_BOT_SANCTUARY_REDIS_USERNAME`/`PASSWORD` added to `setup.sh`'s `get_masked_config_variables()`. `requirements.txt` gained `redis==5.2.1` (same pinned version as `telegram_gateway`).
    - `close_redis_connection()` added and called from `terminate_application()` for lifecycle symmetry with the RabbitMQ side - a safe no-op if the lazy connection was never actually opened.
- [x] **Self-resetting counter/cooldown implemented via a fixed Redis TTL fallback, entirely self-contained to this application - no `telegram_gateway` signal involved.**
  - **Context:** an earlier attempt at "clear the cooldown when the gateway recovers" required a new cross-service event pushed by `telegram_gateway` (a `gateway_recovered` message) - that entire change was reverted at the user's explicit instruction not to touch `telegram_gateway`. The user then asked (paraphrased): "if [the occurrence counter] does not increment ... for let's say 3 times, remove that 24 hour cooldown and revert the count to 0" - the goal being the same as before (a resolved incident's cooldown shouldn't suppress a future, unrelated one), inferred purely from the *absence* of further `gateway_alert` occurrences rather than an explicit recovery signal.
  - **First implementation attempt (superseded): a sliding TTL, refreshed on every occurrence, of `GATEWAY_ALERT_NOTIFY_COOLDOWN_SECONDS * GATEWAY_ALERT_RESET_AFTER_QUIET_CYCLES` (a new setting, default `3` → 3 days).** **User-identified flaw:** a TTL that gets renewed (via `EXPIRE`) every time a new occurrence arrives can never actually lapse for as long as occurrences kept arriving at all - i.e. it silently assumed data would eventually stop coming in, with no fallback at all if that assumption didn't hold (a sustained, unbroken run of occurrences would keep the window open indefinitely). Superseded by the fix below; `GATEWAY_ALERT_RESET_AFTER_QUIET_CYCLES` was removed again as a result (no longer needed).
  - **Current implementation: a fixed, one-time TTL of exactly `GATEWAY_ALERT_NOTIFY_COOLDOWN_SECONDS` (24h by default), applied once per fresh window and never extended afterwards - a guaranteed ceiling regardless of how much more data arrives in between.**
    - `record_gateway_alert_occurrence()`: `INCR`s `_COUNT_KEY` as before, then checks `TTL(_COUNT_KEY) < 0` (i.e. the key exists with no expiry yet - true only the first time a fresh window's counter is created) and only then applies `EXPIRE`. Every subsequent occurrence within that same window still increments the counter but does **not** touch its TTL - so the counter always reverts to 0 exactly `GATEWAY_ALERT_NOTIFY_COOLDOWN_SECONDS` after the window's first occurrence, full stop.
    - `mark_gateway_alert_notified()`: sets `_LAST_NOTIFIED_KEY` with `SET ... EX=GATEWAY_ALERT_NOTIFY_COOLDOWN_SECONDS` directly on every successful notification - since this only ever runs once per notification (not once per occurrence), the TTL is inherently non-renewed already; the write itself simply carries the same fixed window.
    - `should_notify_gateway_alert()`'s own time-diff comparison is left in place, unchanged, as a secondary/clock-skew guard - now largely redundant in practice since the TTL enforces the identical window on its own, but kept rather than removed since it costs nothing and doesn't rely on Redis's clock matching the application's.
  - **Why a fixed TTL over a background thread/scheduler:** still avoids adding any new periodic task, timer thread, or polling loop to an otherwise purely event-driven consumer - the reset is a side effect Redis performs on its own on a fixed schedule, not something this module has to actively track or a background job has to sweep for.
  - This deliberately changes the occurrence counter's semantics from a pure lifetime tally (its original description) to "occurrences within the current fixed 24h window" - an explicit, intentional trade-off per this instruction, not an oversight.

## 5. Agent "Call" model

- [ ] Named roles: **Rukia Call** (entry/default, conversation & routing only), **Architect Call**, **Coder Call**, **Review Call**, **Documentation Call**.
- [ ] Any Call may respond directly or hand off to another Call.
- [ ] Per-thread main loop: if the active Call doesn't resolve the task, hand off to the next Call; that Call can hand back — a bounded back-and-forth ("agent call"), not a strict one-way pipeline.
- [ ] **Corrected — whitelist enforcement moved to `telegram_gateway`, not owned here.** `telegram_gateway` is the only component that actually knows chat_id identity, and it already has the exact precedent pattern (`SESSION_RESET_ALLOWED_CHAT_IDS`, same comma-separated-env-var → `set[int]` style). `bot_sanctuary` does **not** read an env var or perform its own lookup — it trusts an access-tier field stamped onto the inbound task payload by `telegram_gateway` (see follow-up item added to `telegram_gateway/CODE_TODO.md`).
  - A non-whitelisted user's task arrives tagged Rukia-only — no handoff, no access to Architect/Coder/Review/Documentation, effectively a single-agent conversational experience with no repository access (see section 6).
  - A whitelisted user's task arrives tagged for the full Call-handoff graph.
  - **Note the behavioural difference from `SESSION_RESET_ALLOWED_CHAT_IDS`'s pattern:** that whitelist silently drops a disallowed request entirely (log only, no action). This one does not reject anything — the task still proceeds normally, just scoped to Rukia only. It's a tagging/tiering mechanism, not a gate.
- [ ] Each agent gets a defined tool set with explicit specs, so the model can call them directly with no extra glue per tool.

## 6. Workspace / repository access

- [ ] No `session_id`-based folder structure — session IDs are ephemeral and unsuitable as a persistent directory key.
- [ ] **Confirmed — single-user assumption:** the repository directory is wide open to the container; no per-session or per-user filesystem isolation is required.
- [ ] **Confirmed: Rukia has no access to the repository/container filesystem or code tools at all.** It is a conversation/routing-only role. Only the specialised Calls (Architect/Coder/Review/Documentation) get filesystem/tool access. This is also what makes a non-whitelisted user's Rukia-only restriction meaningful as an access boundary, not just a routing default.
