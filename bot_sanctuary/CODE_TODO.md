# TODO Record for Bot Sanctuary

## Purpose

`bot_sanctuary` is the successor to `bot_orchestrator`'s routing role, merged with the AI agent pipeline itself — one consolidated Python application rather than a separate orchestrator container plus per-agent containers. It owns: RabbitMQ consumption from `telegram_gateway`, per-session threading, the multi-agent "Call" pipeline (via the Claude Agent SDK), tool access, and error/alert routing.

**Confirmed:** `bot_orchestrator_application` is being retired in favour of this single application. `bot_orchestrator`'s already-planned responsibilities (SMTP alerting, session-reset broadcast, task routing, outbound payload validation — see its own `CODE_TODO.md`) are absorbed here, refined per the sections below.

Status: **Partially implemented, in progress.** Container/runtime (§1), RabbitMQ + threading (§3), and SMTP-based error handling (§4) are largely built - see each section's own status line for specifics. The agent Call pipeline itself (§5) is not yet implemented; several items below remain proposed and awaiting confirmation, marked accordingly.

- [ ] Credential resolution order, checked at each `start_new_session()` call:
  1. `CLAUDE_CODE_OAUTH_TOKEN` environment variable, if present (covers a future/optional injection path — not used by default, but the resolver doesn't hard-block it).
  2. Else, read `${CLAUDE_CONFIG_DIR}/oauth_token` from disk.
  3. Else — **container does not crash or exit.** The main process (queue consumer, exec-accessible shell) stays alive; only that specific session request goes into a pending/"waiting for authentication" state until a credential becomes available. Open sub-decision: auto-retry on an interval vs. only re-check on next explicit trigger — not yet decided.
- [ ] **Note (not a container-security boundary):** the OAuth token is a portable bearer credential, not device/container-bound — anyone holding the string can use it from anywhere until expiry/revocation. - [ ] `setup-token` chosen deliberately over `/login` — avoids the documented `--print` mode OAuth refresh bug (access token expiry ~8h, refresh not persisted correctly in headless/print automation). `setup-token`'s long-lived (1-year) static token sidesteps this.

### New: message coalescing, and the task_id-orphaning issue it creates

**Context - why coalescing at all.** `telegram_gateway` already combines every media upload with its finalising caption/text into one task before ever pushing it (see its own README's draft-flow docs) - by the time a task reaches `bot_sanctuary`, it is always one complete unit already. The one case with no equivalent combining is plain text: every text update becomes its own `task_id`/RabbitMQ message immediately, with no debounce. Discussed at length in chat (not reproduced in full here): a fixed-delay debounce in `telegram_gateway` was considered and rejected - it taxes every message with latency to solve a rare case, reintroduces the exact "renewed timer never expires" bug this project has already hit and fixed twice elsewhere (`POLL_GLOBAL_CAP_SECONDS`, the `gateway_alert` throttle's own non-renewed TTL), needs new persisted-timer infrastructure `telegram_gateway` shouldn't own, and weakens `session_reset`'s open-task protection (a message sitting in an undeclared debounce buffer has no `task_id` yet, so `has_open_tasks()` can't see it). **Decided instead: coalesce at `bot_sanctuary`'s own dequeue time** - `SessionWorker._run()` blocks for one message, then non-blockingly drains whatever else is already queued (`Option A` - checked right before/at the point a turn would start, not via a fixed timer) into one combined batch. Zero added latency for the common single-message case; only ever combines what's genuinely already waiting.

**The issue this creates, flagged and now resolved:** each message in a coalesced batch still carries its own distinct `task_id` from `telegram_gateway`. If the whole batch is treated as one turn and only acknowledged once the (eventual) agent reply is ready, every `task_id` except the reply's own would stay "open" under `telegram_gateway`'s `session_tasks:<chat_id>` for the *entire* turn duration - and if the reply is only ever published against one `task_id`, the others would never close at all, permanently blocking a future `session_reset` for that chat (deferred forever, until `PENDING_RESET_MAX_WAIT_SECONDS` eventually force-applies it - self-healing, but not clean).

**Resolution (user's proposal, implemented):** every `task_id` in a coalesced batch *except the last* is closed out immediately - `{"task_id": ..., "type": "completed"}` (`telegram_gateway`'s existing terminal marker: "no further payloads are expected... triggers cleanup only", no reply sent) - published on a **separate, short-lived thread** (`_close_intermediate_task_ids()`), concurrently with whatever the `SessionWorker`'s own thread does next, so this never delays the actual turn. Only the batch's **last** `task_id` stays open and is the one the eventual real reply (§5) must be published against. This required zero `telegram_gateway` changes - `completed`'s existing contract already does exactly what's needed.
  - **Why a separate, disposable `RabbitMQPublisher` for the closer thread, not the `SessionWorker`'s own:** `RabbitMQPublisher` is documented as confined to exactly one thread for its whole life; sharing the `SessionWorker`'s long-lived instance across two threads would violate that. The closer thread creates, uses, and closes its own instance instead - a small, bounded, infrequent extra connection cost (only when a batch actually has more than one message), not a hot-path concern.
  - Each successfully-closed intermediate `task_id` also calls `mark_task_complete()` (see the new crash-recovery tracking below) - a byproduct of this mechanism is that part of that tracking's "mark complete" hook is *already* wired, ahead of §5, for every task_id closed this way. Only the batch's final `task_id` still depends on §5 to ever call it.

### Open decisions - three of four now decided and implemented; stray-message handling still on hold

- [x] **Inbox overflow - decided and implemented.** Each `SessionWorker`'s inbox is a bounded `queue.Queue(maxsize=SESSION_INBOX_MAX_SIZE)` (new `config.py` setting, default `100`). Overflow is drop-newest with a `logger.critical()` - chosen over blocking `put()`, which would stall the single shared RabbitMQ consumer thread (and therefore every other session, plus `gateway_alert`/`gateway_recover`) behind one stuck session's full inbox.
- [x] **RabbitMQ ack timing - decided ("return Ack after successfully registering into queue of that session's mailbox") and implemented.** `_dispatch_to_session()` calls `submit()`; a successful registration (`True`) returns normally and `process_message()`'s caller acks right after, same as every other message type. A failed registration (`submit()` returns `False` - inbox full) now **raises** instead of being silently swallowed, so the message is *not* acked - it propagates to `queue_consume_task()`'s existing generic handler, which nacks with requeue up to `Q_CONSUME_MAX_ATTEMPTS` before finally dropping it (no `queue.py` changes needed). A missing `session_id` remains a plain logged drop, not a raise - it's permanently malformed, not transient, so redelivery would never help. At-least-once still weakens for whatever's sitting queued-but-unprocessed at the moment of a crash (an already-acked, already-registered message) - that gap is what the crash-recovery tracking above exists to detect and recover from after the fact, rather than trying to prevent (a deferred-ack alternative was considered and rejected in chat - it needs `add_callback_threadsafe()` cross-thread ack plumbing, a lock around the RabbitMQ consumer's own per-message retry counter, and introduces its own new correctness gap: a delivery_tag becomes stale/invalid across a consumer reconnect, which already happens automatically on a dropped connection).
- [ ] **Stray message after `session_cleared`. On hold, per explicit instruction - no change.** `get_or_create_session_worker()`'s "create if missing" would resurrect a worker for a late message tagged with an already-cleared `session_id`, rather than recognising it as stray and dropping it. Narrow risk in practice (`telegram_gateway` never reuses a `session_id` after a reset, so this only bites on genuine out-of-order delivery) - accepted for now, revisit if ever observed.
- [x] **Shutdown behaviour for in-flight workers - decided ("send shutdown signal to all thread to inform them to finish last task before closing; last task will be marked completed when a response is given to telegram_gateway") and implemented.** `SessionWorker` now has two independent stop paths, not one:
  - `stop()` (unchanged) - immediate, sets a `threading.Event`, abandons whatever else is queued. Still the one used by `_handle_session_cleared()` - correct there, since `telegram_gateway` has already wiped that `session_id` on its own side, so anything left queued would only ever produce an orphaned reply.
  - `shutdown()` (new) - sets a second, independent `threading.Event`. The run loop keeps draining and processing whatever's queued, batch by batch, without waiting, until the inbox is genuinely empty *and* `shutdown()` has been called - so a backlog queued right as shutdown begins is still fully processed, not just whatever batch was already in flight. Every item drained this way was already acked off RabbitMQ (per the ack-timing decision above), so abandoning it here would be a real message loss, not a stale/orphaned one - the opposite judgement from `stop()`.
  - New `shutdown_all_session_workers()` (`utils_session/session_worker.py`) - snapshots the session registry, calls `shutdown()` on every worker, then `join()`s each thread (bounded by new `config.py` setting `SESSION_SHUTDOWN_TIMEOUT_SECONDS`, default `30`s, `0` = wait indefinitely). A worker still alive once its timeout elapses is logged and abandoned - the process exits regardless, since this only ever runs from `terminate_application()`.
  - Wired into `utilities/initialise.py::terminate_application()` **after** `stop_queue_consumer()` (so no new task can reach a worker already shutting down) and **before** `close_rabbitmq_connection()`/`close_redis_connection()` (a worker finishing its last batch may still need to publish and call `mark_task_complete()`).
  - **"Last task marked completed when a response is given to telegram_gateway" is a structural link to §5, not yet literal** - `_process_batch()` today only logs what it would do (§5 doesn't exist yet); once it does, and runs synchronously inside the run loop as it does now, `join()`ing a worker's thread here is exactly what lets an in-flight turn actually finish (publish the real reply, call `mark_task_complete()`) before the process exits, rather than its daemon thread being cut off mid-turn by the interpreter shutting down underneath it.

- [ ] **New (2026-09-10): a possible fixed/scheduled session-reset time, configured on this side.** Raised by the user as the second of exactly two legitimate paths to a session ever being cleared — the other being `telegram_gateway`'s admin-triggered global reset (see its `CODE_TODO.md`'s new `BUG` entry at the top of the file). Nothing about this is designed yet: whether it's a single fixed wall-clock time (e.g. reset everything nightly) or a per-session TTL-style expiry, whether it would itself publish `session_reset` per affected `session_id` the same way `resync_orphaned_sessions()` already does for crash-recovery, and how it'd resolve `session_id → chat_id` for that publish given `bot_sanctuary` is deliberately identity-blind (it may not need to — `session_reset`'s payload only ever carried `task_id`, not `chat_id`, precisely so `bot_sanctuary` never needs chat identity to request one). **Partially answered (2026-09-11):** the "how would it resolve chat identity" question is now answered — it wouldn't need to; `telegram_gateway` resolves `session_id → chat_id` itself, per the "NEW — `session_clear_request` handling" entry below (built for the admin-triggered path, but the same `session_reset`-per-session-cleared shape would apply equally to a future scheduled trigger). The scheduling mechanism itself remains undesigned. Not started; tracked here as a placeholder until designed.

## NEW — `session_clear_request` handling (admin-triggered global session clear, counterpart to `telegram_gateway`'s `"${BOT_NAME} refresh yourself"` command)

Status: **Design finalised (2026-09-11), cross-service with `telegram_gateway` — see its own `CODE_TODO.md`'s BUG entry at the top of that file. Not yet implemented — documented only.** This entry replaces two earlier same-day drafts wholesale (payload schema, `shutdown_all_session_workers()` reuse, sequencing, ack reliance, duplicate-request handling, and crash recovery were each revised at least once - see `telegram_gateway/CODE_TODO.md`'s counterpart entry for the parallel history on that side).

### Blocking dependency on §5 (unchanged, still applies)

`SessionWorker._process_batch()` (§3) today only logs what it would do — no LLM call, no `completed`/`error` ever actually published. This means the new dedicated clearing method below (see Decisions) and an immediate abandon are **behaviourally identical today** — there is no real in-flight work for either to differ over yet. The scaffolding can still be built ahead of §5 (same staging precedent as §3's on-disk directory work), but its entire point only has an observable effect once §5 exists and actually completes turns.

### Goal

A whitelisted admin chat can type `"${BOT_NAME} refresh yourself"` in Telegram to trigger a global clear of every session this application is currently holding. `telegram_gateway` detects the command and whitelist-gates it; this application decides whether to accept or ignore the request, clears its own session state, and notifies `telegram_gateway` per session as each is actually cleared.

### Context

`telegram_gateway`'s own `SESSION_RESET_ALLOWED_CHAT_IDS` whitelist was found to conflate "does the *target* chat get to reset itself" with "is the *requester* an admin allowed to trigger a *global* reset" — see its `CODE_TODO.md`'s BUG entry. The corrected design moves the whitelist check to the point the command is first typed (`telegram_gateway`), and needs a new round-trip: `telegram_gateway` asks (`session_clear_request`), this application acts and clears its own state first, then tells `telegram_gateway` per session (`session_reset`).

Two design directions were explored and rejected during this same discussion, kept here for history:
- **This application enumerating every active `session_id` and handing `telegram_gateway` an explicit target list.** Rejected — `telegram_gateway` already owns the `chat_id ↔ session_id` mapping and resolves/enumerates targets itself (see its own `CODE_TODO.md`'s Part 0/Part 4).
- **`telegram_gateway` force-clearing every stuck chat on crash recovery via `_force_apply_session_reset()`.** Rejected in favour of a more precise mechanism (`bot_started`, see below) — `_force_apply_session_reset()` remains untouched, but only as a last-resort fallback, not the primary recovery path for this feature.

### Decisions

- **Inbound `session_clear_request` — accept or ignore, decided purely from whether a sweep is already in progress.**
  - **Accept** (no sweep currently running): snapshot every `session_id` currently in the registry (`session_worker.py`'s `_sessions`), mark a sweep in progress, and signal every one of them **concurrently** — not sequentially, not one-at-a-time-waiting. "Iteratively" in an earlier draft of this entry was corrected by the user to mean *every* session finishes on its own, independently, not one blocking the next.
  - **Ignore** (a sweep is already running): the *only* case this application ever sends a literal `completed`/`error` for this feature — closes out the *incoming* `session_clear_request`'s own `task_id` so it doesn't hang, and does nothing else. **In the accepted/normal path, no separate `completed`/`error` is ever sent** — see the `session_reset` payload note below for why one isn't needed.
  - No other business logic beyond this accept/ignore check — only a whitelisted admin can reach this at all (gated once, upstream, by `telegram_gateway`).
- **A new, dedicated `SessionWorker` method — not a reuse of `shutdown()`/`stop()` with a flag, per explicit instruction.** A third terminal path alongside the existing two:
  - `stop()` — immediate, abandons whatever's queued (unchanged, still used by `_handle_session_cleared()`).
  - `shutdown()` — graceful drain, no publish/clear on exit (unchanged, still used by `shutdown_all_session_workers()` at process-terminate).
  - **New method (name TBD)** — same draining behaviour as `shutdown()` (finish everything queued, no abandonment), but its exit action always publishes `session_reset` and clears local state — no flag needed, since the method's own existence is the signal. Needs its own dedicated `threading.Event` (a third one, alongside `_stop_event`/`_shutdown_event`) and its own branch in `_run()`'s exit condition.
  - **Re-verified: `shutdown_all_session_workers()` cannot be reused for this at all, in any form.** It only calls `worker.shutdown()` then joins each thread — no publish, no `clear_session_directory()`, no registry removal (correct for its own purpose; the process is exiting anyway). None of that carries over here, which is exactly why a genuinely new method is needed rather than a parameterised `shutdown()`.
- **Why graceful (not immediate) — recorded since it was asked directly, not just a preference:** `telegram_gateway`'s existing deferred-reset machinery (§0-§8, its own `CODE_TODO.md`) only unblocks once a `completed`/`error`-equivalent actually arrives for a chat's open task. If this application abandoned an in-flight turn instead of finishing it, that signal would simply never come, and the chat would sit deferred until `telegram_gateway`'s own timeout backstop eventually force-applies it — a real regression (silently lost reply, needlessly delayed reset). Finishing gracefully first means the common case never even needs `telegram_gateway`'s defer path to engage — by the time `session_reset` is published, the chat's last open task is already closing with it.
- **`session_reset` payload — carries the session's last `task_id` when one exists, and this is deliberate, not incidental:** `{"task_id": <last task_id, if any, else null>, "session_id": <cleared>, "type": "session_reset"}`. Per the confirmed design, **`telegram_gateway` treats this message as the `completed`/`error` for that `task_id`** when one is present — this is *why* no separate `completed`/`error` is sent in the accepted path (see Decisions above): `session_reset` already does that job. Only when a session was genuinely idle (nothing queued, no `task_id` to attach) does it go out as `task_id: null`, and `telegram_gateway` resolves that chat via `session_id` instead (its own Part 0).
  - **Re-verified: `session_id` is a new field on this payload, not already there.** `resync_orphaned_sessions()`'s current publish is `{"task_id": task_ids[0], "type": "session_reset"}` — no `session_id`. This is a real, if small, schema change shared by both publishers.
  - **Low-cost follow-on worth doing at the same time:** `resync_orphaned_sessions()` already has `session_id` in scope in its own loop — a one-line addition gives that existing path the same resilience benefit, not required but cheap to fold in rather than leave the two publishers of the same type on different shapes.
  - Uses its own disposable `RabbitMQPublisher` instance per publish, same pattern `resync_orphaned_sessions()`/`_close_intermediate_task_ids()` already use — not the long-lived, thread-confined one a `SessionWorker` owns for its own turn traffic.
- **Sweep-in-progress tracking — entirely internal to this application, plain in-memory, never dependent on anything from `telegram_gateway`.** Each session, once it publishes its own `session_reset` and clears its own local state, **logs that it performed its reset** and reports in against a shared counter/set (the snapshot taken at accept-time). The sweep-in-progress flag clears once every snapshotted session has reported in exactly once. No reliance on `telegram_gateway`'s `session_cleared` ack for this or anything else — `_handle_session_cleared()` still exists and is still idempotent against an already-removed session, but this feature does not wait on or need it.
- **No cross-process recovery of an interrupted sweep, deliberately — this is a correction from an earlier draft of this entry.** Once this application consumes/acks a RabbitMQ message, its content is gone if the process crashes before finishing — there is nothing concrete to "resume" on restart, and no attempt is made to. The in-memory sweep-in-progress flag/snapshot is simply lost on any restart, same as any other in-memory state. **New `bot_started` event (see below) is the entire extent of what this application does about a crash mid-sweep** — a one-way, unconditional "I'm alive" broadcast, with all reconciliation happening on `telegram_gateway`'s side.
- **New `bot_started` event, fired unconditionally at the very start of `initialise_application()`** (ahead of the existing `resync_orphaned_sessions()` call — see Open Questions for exact ordering confirmation) — `{"type": "bot_started"}`, no other fields. Not scoped to this feature specifically; fires on every startup regardless of cause (crash or a routine redeploy), since either way this application has no memory of what it was doing before.
- **The existing `mark_task_active`/`mark_task_complete`/`sweep_orphaned_sessions`/`resync_orphaned_sessions()` mechanism is unrelated and untouched by this feature.** It keeps doing its own generic job for ordinary orphaned tasks (admin-sweep-related or not) exactly as it does today — this feature neither relies on it nor changes it. `bot_started` is a separate, additive signal.

### Open Questions

1. Exact name for the new dedicated `SessionWorker` method.
2. Concurrent-signal mechanics — how the shared "sweep in progress" counter/set is structured (a plain `int` count-down under a lock, vs. a set of remaining `session_id`s removed as each reports in) — a small implementation detail, not a design ambiguity.
3. Whether a second `session_clear_request` arriving in the narrow window *between* accepting and actually finishing the snapshot/signal step (rather than clearly before-or-after a sweep) needs any special handling, or whether the plain in-progress flag already covers it correctly by construction — likely already fine, not deeply examined yet.
4. **From the §5 dependency above:** whether to build this feature's scaffolding now (behaviourally inert until §5 exists) or wait until §5 lands so the graceful-vs-immediate distinction can be verified against real behaviour. No default assumed - precedent exists both ways elsewhere in this file.
5. Exact ordering of `bot_started` vs. `resync_orphaned_sessions()` at startup — see `telegram_gateway/CODE_TODO.md`'s Part 5, which currently assumes `bot_started` fires first.
